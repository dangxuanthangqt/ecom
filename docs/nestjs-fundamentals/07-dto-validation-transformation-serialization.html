02Vì sao DTO bắt buộc phải là class

"DTO chỉ mô tả hình dạng, sao không dùng interface cho nhẹ?" — Vì interface biến mất sau khi biên dịch, mà cả hai thư viện đều cần đọc thông tin lúc chạy.

Nối về chương 1 §5: nhờ emitDecoratorMetadata, Nest lấy kiểu của tham số @Body() từ design:paramtypes và truyền cho pipe dưới tên metatype. ValidationPipe mở đầu bằng câu hỏi: metatype này có phải class có decorator không? Nếu không — nó không làm gì cả: 

6. metatype = Object → bỏ qua, trả nguyên: {"x":1}
Hệ quả rất thực tế
Khai @Body() body: SomeInterface thì metatype là Object, pipe im lặng bỏ qua, và endpoint của bạn không hề được validate — không lỗi, không cảnh báo. Loại bug tệ nhất: nó trông như đang hoạt động.

Cùng lý do, String, Number, Boolean, Array, Object đều bị bỏ qua. Validate tham số nguyên thuỷ thì dùng pipe riêng (ParseUUIDPipe, ParseIntPipe).

03Chiều vào: ValidationPipe
src/shared/utils/validation-pipe.config.tsdòng 15-22 
export const validationPipeOptions: ValidationPipeOptions = {
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: true,
  errorHttpStatusCode: HttpStatus.BAD_REQUEST,
  exceptionFactory: (errors) => new ValidateException(transformValidateObject(errors)),
};

Năm dòng, mỗi dòng một quyết định. Bảng dưới là kết quả chạy thật với input { name: "a", pageSize: "10", hacker: 1 }:

Cấu hình Kết quả Nhận xét
mặc định (không cờ nào) {"name":"a","pageSize":"10","hacker":1} field lạ đi thẳng vào service
whitelist: true {"name":"a","pageSize":10} hacker bị lược im lặng
whitelist + forbidNonWhitelisted THROW ["property hacker should not exist"] báo lỗi thay vì lược
transform: false {"pageSize":"10"}, instanceof Dto = false trả object thường
transform: true {"pageSize":10}, instanceof Dto = true trả instance DTO thật
whitelist — mặc định là bỏ

Không bật, mọi field client gửi đều lọt vào service. Đó là chỗ sinh lỗ hổng mass assignment: client thêm {"isSystem": true} vào body, và nếu service spread thẳng xuống Prisma thì field đó được ghi.

Bật lên: chỉ field có decorator validate mới đi qua.

forbidNonWhitelisted — báo thay vì lược

Lược im lặng thì client gửi sai tên field (pageSizes) sẽ thấy API "không nhận giá trị của tôi" mà không hiểu vì sao. Bật lên, họ nhận property pageSizes should not exist.

transform — và query string

HTTP không có kiểu. ?pageSize=10 đến server là chuỗi "10", luôn luôn. Không transform, @IsInt() trượt với mọi request.

src/dtos/shared/pagination.dto.tsdòng 40-45 
@ApiPropertyOptional({ description: "Number of items per page", example: 20 })
@IsInt({ message: "pageSize must be an integer" })
@Type(() => Number)          // ← chuỗi "10" → số 10, TRƯỚC khi validate
@IsPositive({ message: "pageSize must be greater than 0" })
@IsOptional()
pageSize?: number;

Thứ tự thật sự xảy ra: transform trước, validate sau. Và transform: true còn có tác dụng thứ hai, quan trọng cho mục 6: giá trị handler nhận được là instance của DTO class.

@ValidatorConstraint({ name: "mutuallyExclusive", async: false })

  defaultMessage(args) { /* … */ }

async: true — cân nhắc kỹ
Class-constraint hỗ trợ validate cần I/O ("email này đã tồn tại chưa"). Nhưng nó đưa truy vấn vào tầng pipe, và tạo race condition kinh điển — kiểm "chưa tồn tại" rồi insert vẫn có thể đụng unique constraint. Dự án chọn cách khác: để DB làm trọng tài, map P2002 → 409.

06Serialization: chiều ra
Mục quan trọng nhất của chương. Đọc kỹ.

excludeExtraneousValues: true nghĩa là chỉ field có @Expose() mới ra ngoài — mặc định không lộ gì, phải khai mới lộ. Nhưng có một điều kiện mà rất nhiều người bỏ sót.

ClassSerializerInterceptor — mã nguồn Nest, rút gọn 
serialize(response, options) {
  if (!isObject(response) || response instanceof StreamableFile) return response;
  return Array.isArray(response)
    ? response.map(item => this.transformToPlain(item, options))
    : this.transformToPlain(response, options);
}

Nó gọi classToPlain lên bất cứ thứ gì handler trả về. Vậy nếu handler trả object Prisma thô thay vì instance DTO thì sao?

Trực giác sai — và kết quả chạy thật

Nhiều người (kể cả tôi khi viết chương 5 lần đầu) đoán "không có @Expose() nào, chắc bị lọc thành {}". Sai. 

1. instance DTO + excludeExtraneousValues:
    { id: 'r1', name: 'admin' }                                    ← password, secret bị bỏ ✓
2. object THÔ (không phải instance) + excludeExtraneousValues:
    { id: 'r1', name: 'admin', password: 'hash', secret: 'x' }     ← LỘ HẾT ✗
3. instance DTO, KHÔNG bật cờ:
    { id: 'r1', name: 'admin', password: 'hash', secret: 'x' }     ← LỘ HẾT ✗
4. DTO lồng object thô bên trong:
    { inner: { id: 'r1', name: 'admin', password: 'hash', secret: 'x' } }  ← LỘ HẾT ✗

excludeExtraneousValues áp luật @Expose() của một class. Object thường không thuộc class nào → không có luật nào để áp → đi thẳng ra nguyên vẹn.

Hỏng ở đây hỏng theo hướng lộ dữ liệu, không phải mất dữ liệu. Không exception, không log, response trông vẫn hợp lệ. Bạn chỉ phát hiện khi ai đó mở DevTools và thấy password trong JSON.

// Wrap each row in the response DTO so ClassSerializerInterceptor
// (excludeExtraneousValues) can actually strip fields — it only

Lúc chạy, class-transformer không biết T là gì. Nên data phải đã là mảng instance DTO trước khi vào đây — PageDto không tự bọc hộ. Swagger cũng không suy ra được T, phải khai tay bằng ApiExtraModels + getSchemaPath (mục 9).

07DTO lồng nhau và cái bẫy @Type

Khi một field là object, class-transformer không biết phải dựng nó thành class nào — kiểu TypeScript đã bị xoá. Bạn phải nói bằng @Type().

Trường hợp Input Kết quả (cấu hình thật của dự án)
Có @Type, inner sai kiểu { inner: { code: 123 } } {"field":"inner.code","code":"isString","message":"code must be a string"}
Có @Type, inner đúng { inner: { code: "ok" } } OK, inner instanceof Inner = true
Thiếu @Type, inner sai kiểu { inner: { code: 123 } } "property code should not exist"
Dòng cuối là chỗ người mới mất cả buổi
Lỗi nói property code should not exist — nghe như bạn gửi thừa field. Sự thật hoàn toàn khác: vì không có @Type(), class-transformer không dựng inner thành Inner, nên whitelist nhìn vào và thấy mọi field bên trong đều "không được khai" → lược sạch và báo thừa.

Quy tắc: thấy whitelistValidation / should not exist trên field mà bạn biết chắc đã khai — kiểm ngay xem field cha có @Type(() => …) chưa. Gần như luôn là nguyên nhân.

@Type() cũng là thứ đã dùng cho pageSize ở mục 3 — cùng một decorator, hai công dụng: đổi kiểu nguyên thuỷ, và chỉ định class cho object lồng.

08Pipe tự viết, và luồng upload file
src/shared/pipes/image-validation.pipe.tsrút gọn 
@Injectable()
export class ImageValidationPipe implements PipeTransform {
  transform(file: Express.Multer.File) {
    if (!file) throw new BadRequestException("File is required.");
    if (file.size > this.maxSize) throw new BadRequestException(`File too large…`);
    if (!this.allowedMimeTypes.includes(file.mimetype)) throw new BadRequestException(/* … */);
    return file;       // ← trả về GIÁ TRỊ handler sẽ nhận
  }
}

Pipe khác guard ở chỗ: guard trả boolean (cho qua hay không), pipe trả giá trị (có thể đã biến đổi). Pipe là nơi duy nhất vừa validate vừa transform một tham số cụ thể.

Hệ quả khó chịu của thứ tự đó — comment ở media.controller.ts:60-62
"If validate with pipe in @UploadedFile, file size will be available, but it will be after the file is uploaded. Now file is uploaded to disk first, then validated."

Pipe không ngăn được file 2 GB được ghi ra đĩa — nó chỉ từ chối sau khi ghi xong. Muốn chặn sớm, giới hạn phải đặt ở chính multer (limits.fileSize), tức ở interceptor. Ví dụ tốt cho nguyên tắc chương 5 §6: sớm nhất có thể, nhưng không sớm hơn dữ liệu bạn cần.

Repo cũng ghi nhận lý do chọn disk thay vì buffer: "buffer will cause memory issue (OUT OF MEMORY) when uploading large files". Ba pipe file: ImageValidationPipe (một file), MultipleFilesValidationPipe, ArrayFilesValidationPipe (mảng, có cấu hình nên phải new tại chỗ dùng).

Pipe có sẵn
ParseUUIDPipe chặn id rác trước khi chạm DB — không có nó, id sai định dạng thành lỗi Prisma và ra 500 thay vì 400. Anh em: ParseIntPipe, ParseBoolPipe, ParseArrayPipe, ParseEnumPipe, DefaultValuePipe.
09Swagger ăn theo DTO

DTO phục vụ ba khách hàng, không phải hai: validate, serialize, và sinh tài liệu API. Ba composite decorator gói sẵn hợp đồng lỗi cho ba nhóm route (chương 1 §9): ApiAuth (có 401/403), ApiPublic (không), ApiPageOkResponse (danh sách phân trang — ghép tay ApiExtraModels + getSchemaPath + allOf vì Swagger không suy ra được T).

đừng quên sau khi đổi DTObash 
pnpm build:swagger   # sinh lại swagger.yaml
pnpm build:schema    # swagger.yaml → schema.ts cho frontend

Bỏ qua thì swagger.yaml (265 KB) và schema.ts (204 KB) lệch với code, và frontend gõ theo kiểu cũ.

10Nâng cao và những chỗ dễ vấp
Request và response nên là hai class

Trộn chung thì @Expose() và @Is... nằm lẫn, và field chỉ dành cho input (confirmPassword) có nguy cơ bị expose ra response. Repo đang tách đúng.

@Exclude() gần như thừa

Với excludeExtraneousValues: true, không @Expose() là đã bị loại. @Exclude() chỉ có nghĩa ở class không bật cờ đó.

Đổi tên / đổi giá trị khi ra

@Expose({ name: "created_at" }) đổi tên field; @Transform(({ value }) => …) đổi giá trị. Hữu ích khi hợp đồng API khác tên cột DB.

@SerializeOptions({ groups })

Cùng một DTO lộ nhiều hay ít tuỳ route (kết hợp @Expose({ groups })). Interceptor đọc nó bằng Reflector — lại đúng cơ chế chương 2.

whitelist không cứu nếu service spread body

data: { ...body } xuống Prisma vẫn nguy hiểm nếu một ngày ai đó thêm field vào DTO mà quên nghĩ tới ghi DB. Liệt kê field tường minh ở tầng repository.

@IsOptional() bỏ qua mọi validator khác

khi giá trị là undefined hoặc null. Muốn "cho phép vắng mặt nhưng nếu có thì không được null" thì dùng @ValidateIf((o) => o.x !== undefined).

Thứ tự decorator validate không quan trọng

nhưng @Type() luôn chạy trước mọi @Is... vì nó thuộc pha transform.

transform: true có chi phí

Mỗi request dựng một instance DTO. Không đáng kể ở quy mô này, nhưng là lý do không nên đặt DTO khổng lồ lồng nhiều tầng.

12Tự kiểm chứng — đã chạy thật khi viết
A · serialization (quan trọng nhất)

Code đầy đủ trong bản markdown. Bốn dòng output, chỉ dòng 1 an toàn — ba dòng còn lại đều lộ password và secret, ba cách khác nhau để làm rò dữ liệu mà không có lỗi nào báo.

B · bốn cờ của ValidationPipe

ValidationPipe gọi trực tiếp được, không cần boot Nest. Đối chiếu với bảng ở mục 3: 

1. mặc định, field lạ       → OK    {"name":"a","pageSize":"10","hacker":1} | instance? false
2. whitelist                → OK    {"name":"a","pageSize":10}
3. whitelist+forbidNonWL    → THROW ["property hacker should not exist"]
4. KHÔNG transform          → OK    {"name":"a","pageSize":"10"} | instance? false
5. transform (query string) → OK    {"name":"a","pageSize":10}   | instance? true
6. metatype = Object       → bỏ qua, trả nguyên: {"x":1}
C · bẫy @Type với cấu hình thật

Import thẳng validationPipeOptions từ repo, nên kết quả đúng bằng production. Dòng thứ ba trả property code should not exist — thông điệp không liên quan gì tới nguyên nhân thật là thiếu @Type(). Biết trước điều này tiết kiệm cho bạn nửa buổi debug.
