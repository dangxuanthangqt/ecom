Guard

Nơi kết quả của chương 1 và 2 được dùng để quyết định. Ba câu hỏi ai viết guard cũng phải trả lời: false hay throw, đăng ký kiểu nào để có DI, và khi hạ tầng hỏng thì mở hay đóng.

02return false hay throw?
return false
  • Nest ném ForbiddenException("Forbidden resource") thay bạn

  • Chuyển thẳng cho exception filter

03Guard tối giản trong dự án
src/shared/guards/api-key.guard.tsdòng 13-29 
@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(private readonly appConfigService: AppConfigService) {}

  canActivate(context: ExecutionContext) {
    const request = context.switchToHttp().getRequest<Request>();   // 1. lấy request
    const headerApiKey = request.headers[SECRET_API_KEY];

    if (headerApiKey === "secretApiKey") {                          // 2. kiểm
      return true;                                                // 3a. qua
    }
    throw new UnauthorizedException("API key is invalid.");         // 3b. ném
  }
}

Có DI (AppConfigService) dù dòng đọc config đang bị comment (dòng 21), và chưa route nào dùng — nó nằm đó làm nhánh ApiKey của guard ghép ở mục 7.

04Ba cách đăng ký — và vì sao dự án chọn APP_GUARD
Cách Ở đâu Phạm vi DI
@UseGuards(G) trên method / class controller một route / cả controller Có
app.useGlobalGuards(new G()) main.ts toàn app Không — bạn new bằng tay
{ provide: APP_GUARD, useClass: G } một module toàn app Có — container tạo
src/shared/modules/base.module.tsdòng 43-54 
const guards: Provider[] = [
  AccessTokenGuard,   // provider thường — có trong container để được TIÊM, không tự chạy
  ApiKeyGuard,        // provider thường
  { provide: APP_GUARD, useClass: AppThrottlerGuard },         // ← tự chạy, thứ 1
  { provide: APP_GUARD, useClass: AuthorizationHeaderGuard },  // ← tự chạy, thứ 2
];
Vì sao phải APP_GUARD

AuthorizationHeaderGuard cần Reflector + hai guard con; AccessTokenGuard lại cần TokenService, PermissionResolverService. Với useGlobalGuards(new …) bạn phải tự new cả cây — không làm được.

Guard là hằng số, chính sách là dữ liệu

Dự án không dùng @UseGuards ở đâu cả. Mọi route qua cùng hai guard toàn cục; khác biệt nằm ở metadata (@RequirePermission, @AuthApi, @Throttle), không ở việc gắn guard nào.

Short-circuit

Guard đầu tiên chặn → dừng ngay, guard sau không chạy.

Short-circuit là công cụ thiết kế — base.module.ts:39-42
AppThrottlerGuard đứng trước AuthorizationHeaderGuard. Đảo lại: một cơn lũ request không token vẫn phải qua verify JWT (tốn CPU) trước khi bị rate limit chặn — và rate limiter chỉ đếm những request đã qua auth, tức không đếm được đúng thứ nó sinh ra để chặn.
06Guard nhìn thấy gì — và không thấy gì
Thấy
  • req.body đã qua body-parser → object thô
  • header, query, params (chuỗi thô)
  • metadata handler qua Reflector — siêu năng lực
  • những gì middleware gắn: req.id, req.i18nContext
Không thấy
  • body chưa qua ValidationPipe — chưa whitelist, chưa thành DTO
  • params chưa parse — ParseUUIDPipe chưa chạy
  • kết quả handler (việc của interceptor)
  • giá trị param decorator (chạy sau guard)
Hệ quả
Không validate DTO trong guard — body chưa sạch. AppThrottlerGuard đọc req.body.email làm khoá rate-limit (throttler-options.factory.ts:67-85) và vì thế phải tự phòng thủ: cắt độ dài, chuẩn hoá, không tin kiểu.
07Guard ghép: AuthorizationHeaderGuard

Route có thể cần Bearer, hoặc API key, hoặc không cần gì, hoặc một trong hai. Thay vì mỗi route gắn guard khác nhau: một guard điều phối đọc nhãn rồi gọi guard con.

Đang tải...
Trông như bug: property initializer dùng this.accessTokenGuard

Bảng authorizationTypeMapper (dòng 25-31) tham chiếu tham số constructor trước thân constructor. Không sao: với target: ES2021, TS emit parameter property trước property initializer. Đổi target lên ES2022 + useDefineForClassFields là thứ tự đổi và dòng này thành undefined.

Lỗ hổng thật của nhánh OR + None

[Bearer, None] với OR: token hỏng → AccessTokenGuard ném → bị nuốt → thử None → qua luôn, không kiểm quyền. Boot-check từ chối khởi động khi thấy hình dạng này (permission-coverage.service.ts:44, 55-58). None chỉ được đứng một mình.

Bài học từ guard ghép
Khi gộp nhiều guard, phải quyết định rõ chuyện gì xảy ra khi một guard con fail: nuốt hay lan? OR nuốt (và đánh mất thông điệp chi tiết 401 expired/invalid). AND lan. Câu trả lời ảnh hưởng cả bảo mật lẫn thông điệp lỗi. Đường thường ngày của request: mặc định AND + [Bearer] → gọi AccessTokenGuard đúng một lần.
08Guard kế thừa thư viện: AppThrottlerGuard
src/shared/guards/app-throttler.guard.tsdòng 18-44, rút gọn 
@Injectable()
export class AppThrottlerGuard extends ThrottlerGuard {
  protected throwThrottlingException(context: ExecutionContext, detail: ThrottlerLimitDetail): Promise<void> {
    const response = context.switchToHttp().getResponse<Response>();
    if (!response.headersSent) {
      response.header("Retry-After", String(detail.timeToBlockExpire));   // header TRƯỚC khi throw
    }
    throwHttpException({ type: "tooManyRequests", message: "Too many requests. Please try again later." });
  }
}
Đổi một method, giữ toàn bộ logic

Đếm, lưu Redis, đọc @Throttle() — thư viện làm. Dự án chỉ đổi cách báo lỗi: envelope chung của API thay ThrottlerException, và phát lại Retry-After dưới tên chuẩn.

Metadata của thư viện — cùng cơ chế

@Throttle(AuthThrottle.LOGIN) ở auth.controller.ts:89 là SetMetadata với key của @nestjs/throttler; ThrottlerGuard đọc bằng Reflector. Chương 1-2, chỉ khác người viết. Thông điệp cố ý không nói giới hạn nào bị chạm — oracle miễn phí cho người dò rate limit.

12Nâng cao
Không phải HTTP

getType() trả "rpc"/"ws"; switchToRpc()/switchToWs(). Một guard phục vụ nhiều transport nếu rẽ nhánh theo type.

Class + method cùng chạy

@UseGuards(A) class + @UseGuards(B) method → A rồi B. Guard là cộng dồn, không "đè" như metadata.

Không làm việc nặng / ghi DB

Guard chạy cho mọi request khớp, kể cả request pipe sẽ từ chối ngay sau. Tra đọc có cache thì được; audit log vào DB thì để interceptor/service.

Header trước khi throw

Trả false không sửa được body. Muốn thêm header (Retry-After) → ghi vào response trước khi throw, kiểm headersSent.

@Public() kiểu phổ biến vs cách dự án

Nhiều dự án viết if (isPublic) return true đầu guard auth. Dự án này: public là một loại xác thực (None) trong guard điều phối, và boot-check ép mọi route chọn rõ. Khó quên hơn.

14Tự kiểm chứng
01 · Ba mã lỗi từ một guard
# 401 — không token
curl -s -i localhost:3000/roles | head -1
# 401 — token rác
curl -s -i -H "Authorization: Bearer abc" localhost:3000/roles | head -1
# 403 — token client gọi route admin

  -d '{"email":"<client-email>","password":"<password>"}' | jq -r .accessToken)
curl -s -i -H "Authorization: Bearer $TOKEN" localhost:3000/roles | head -1
02 · Xem short-circuit

Gọi một route với token rác thật nhanh nhiều lần — bạn nhận 429, không phải 401. Rate limiter đứng trước và dừng dây chuyền trước khi auth chạy.
