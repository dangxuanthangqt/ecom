Middleware

Tầng dưới NestJS — nó thuộc về Express. Chạy lúc nào, viết và đăng ký ra sao, khác guard chỗ nào, và trả lời câu hỏi "sao không làm auth bằng middleware cho gọn?"

Express 5.0.10 middleware tự viết4 middleware đang chạy
01Middleware là hàm (req, res, next) của Express
Express thuần
function logRequest(req: Request, res: Response, next: NextFunction) {
  console.log(req.method, req.url);
  next();   // gọi hàm kế tiếp; không gọi là request treo
}
Một quy tắc

Làm việc của mình rồi gọi next(), hoặc tự trả response và không gọi next().

Không ExecutionContext, không Reflector, không khái niệm "handler" — vì đây chưa phải Nest. Đổi lại: cors, helmet, compression, cookie-parser… dùng nguyên xi. Lợi thế lớn nhất là hệ sinh thái.

Nói một lần cho rõ
Middleware không đọc được metadata của handler. Không @RequirePermission, không @AuthApi, không @Throttle. Express đã khớp path để biết có chạy middleware này không, nhưng "handler" theo nghĩa Nest — hàm có metadata — chưa tồn tại trong ngữ cảnh của nó. Bất kỳ quyết định nào cần biết "route này khai gì" không thể nằm ở middleware.

Ngược lại, vì chạy sớm, middleware là chỗ đúng cho việc phải xảy ra với mọi request bất kể đích đến: parse body, gắn request id, mở CORS, phát hiện ngôn ngữ.

03Hai cách viết
Hàm thuần — không DI, gọn 
export function requestTiming(req, res, next) {
  const start = Date.now();
  res.on("finish", () =>
    console.log(`${req.url} ${Date.now() - start}ms`));
  next();
}
Class NestMiddleware — có DI 
@Injectable()
export class RequestTimingMiddleware implements NestMiddleware {
  constructor(private readonly logger: PinoLogger) {}
  use(req, res, next) {
    const start = Date.now();
    res.on("finish", () => this.logger.info({ ms: Date.now() - start }));
    next();
  }
}
04Ba cách đăng ký
Cách Ở đâu DI Chọn route Lỗi ném ra đi đâu
app.use(fn) main.ts Không toàn app Express xử lý — GlobalExceptionFilter không thấy
consumer.apply(M).forRoutes(…) configure() của module Có path / method / controller, có exclude() Nest bọc proxy → về exception filter
Thư viện tự đăng ký module của thư viện Có thư viện quyết như dòng trên
mẫu chuẩn — ví dụ minh hoạ 
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(RequestTimingMiddleware)
      .exclude({ path: "health", method: RequestMethod.GET })   // giả định có route health
      .forRoutes("*path");                                     // Nest 11: wildcard có tên
  }
}
Nest 11 đổi cú pháp wildcard

path-to-regexp v8 yêu cầu wildcard có tên: "*path" hoặc "{*path}". "*" cũ vẫn được tự chuyển (kèm cảnh báo); "/users/*" phải thành "/users/*path".

Module chỉ là nơi đặt code

Middleware trong configure() của một module không bị giới hạn vào route của module đó. forRoutes("*path") áp cho mọi route toàn app.

05Middleware vs Guard vs Interceptor vs Pipe
Middleware Guard Interceptor Pipe
Biết handler nào sắp chạy Không Có Có Có
Đọc metadata handler Không Có Có Có
Thấy body đã validate Không Không Có (sau pipe) chính nó validate
Sửa response Có (thô) Header được, body không Có (map kết quả) Không
Dùng cho log, id, CORS, parse, ngôn ngữ quyền vào cửa serialize, cache validate, transform
Chọn nhanh
"Việc này có cần biết route đích khai gì không?" Có → guard/interceptor/pipe. Không → middleware.
06Vì sao xác thực không phải middleware trong dự án
1 · Public và protected trộn trong một controller

brand.controller.ts: GET /brands public, POST /brands cần brand:create:any. Middleware không biết request rơi vào route nào → phải tự khớp path, tức viết lại router. Guard đọc @IsPublicApi() là xong.

2 · Phân quyền cần @RequirePermission

Middleware không đọc được. Nếu ép, bạn có một bảng path → permission bên ngoài — chính là thiết kế cũ mà lần refactor vừa rồi bỏ đi vì bốn lỗ hổng.

3 · Boot-check chỉ tồn tại nhờ metadata

PermissionCoverageService quét nhãn trên handler. Với middleware, không có gì để quét.

Nói gọn
Middleware trả lời "request này là gì". Guard trả lời "request này được làm gì". Auth là câu thứ hai.
07Bốn middleware đang chạy trong dự án

Không file nào trong src/ implement NestMiddleware. Nhưng mỗi request vẫn đi qua bốn middleware trước khi tới guard — tất cả từ thư viện.

7.1 · body-parser — mặc định của Nest

NestFactory.create() tự đăng ký json + urlencoded. Vì thế req.body trong guard đã là object. Tắt bằng { bodyParser: false }; giữ body thô cho webhook bằng { rawBody: true }.

7.2 · CORS — main.ts:27-32

enableCors gói gọn gói cors và app.use nó. Request OPTIONS (preflight) được trả lời ngay tại đây với 204 — không bao giờ tới guard. Đó là lý do preflight không bị 401.

7.3 · Log + request id — nestjs-pino

LoggerModule tự consumer.apply(pinoHttp).forRoutes("*"). Cấu hình ở setup-logger.util.ts: genReqId (39-48) lấy X-Request-Id client gửi hoặc sinh UUID, ghi ngược lại header response; redact (9-17) che authorization, password, email trước khi ghi log. Redact phải ở middleware — nó cần thấy request thô.

7.4 · Ngôn ngữ — nestjs-i18n

i18n.module.ts:26-30 khai hai resolver (Accept-Language, x-lang). I18nModule đăng ký I18nMiddleware cho mọi route: chạy resolver, gắn req.i18nContext, mở AsyncLocalStorage để I18nContext.current(ctx) ở current-lang.decorator.ts:6 đọc được. Quan hệ ngầm: @CurrentLang() (tầng Nest) phụ thuộc một middleware (tầng Express) đã chạy trước.

Không phải middleware nhưng ảnh hưởng middleware: trust proxy — main.ts:24
Quyết định req.ip là gì, mà req.ip là khoá rate-limit của AppThrottlerGuard. Mặc định "không tin ai": tin thừa một hop là kẻ tấn công giả X-Forwarded-For để có budget mới mỗi request.

08Nếu bạn cần viết một middleware

Ví dụ hợp lệ: chế độ bảo trì — trả 503 cho mọi request trừ một route health check (dự án hiện chưa có route này; ví dụ giả định có), không cần biết route đích.

Code minh hoạ — MaintenanceModeMiddleware + đăng ký 
@Injectable()
export class MaintenanceModeMiddleware implements NestMiddleware {
  constructor(private readonly appConfigService: AppConfigService) {}

  use(req: Request, res: Response, next: NextFunction) {
    if (!this.appConfigService.appConfig.maintenanceMode) return next();

    // Vì đăng ký qua consumer.apply, GlobalExceptionFilter bắt và trả đúng envelope.
    throw new ServiceUnavailableException("Service is under maintenance.");
  }
}

// app.module.ts
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(MaintenanceModeMiddleware)
      .exclude({ path: "health", method: RequestMethod.GET })
      .forRoutes("*path");
  }
}
Checklist trước khi viết
  • Cần biết handler/metadata? → không viết middleware.
  • Cần chạy cho cả request sẽ bị 401/404? → middleware là đúng.
  • Cần DI? → class NestMiddleware + consumer.apply.
  • Muốn lỗi ra đúng envelope? → consumer.apply, không app.use.
  • Nhớ next() ở mọi nhánh không trả response.
09Nâng cao
res.on("finish")

Middleware chạy trước, nhưng đăng ký callback chạy sau — cách pino-http đo responseTime. Đừng await next(): next() của Express không trả Promise.

Lỗi async trong hàm thuần

Express 4 không bắt Promise reject → request treo. Express 5 (Nest 11 dùng) bắt được, nhưng thói quen next(err) hoặc class NestMiddleware vẫn an toàn hơn.

Chạy cả cho route không tồn tại

forRoutes("*path") chạy với path không có controller → rồi mới 404. Vì thế pino có log cả request 404.

Đừng "gắn user vào request" ở middleware rồi guard đọc

Hai chỗ hiểu về token; middleware không biết route có public không nên phải nuốt lỗi → auth im lặng thất bại. Để guard làm cả hai.

11Tự kiểm chứng
01 · Request id đi vòng qua middleware rồi ra header 
curl -s -D - -o /dev/null localhost:3000/products | grep -i x-request-id
curl -s -D - -o /dev/null -H "X-Request-Id: thu-nghiem-123" localhost:3000/products | grep -i x-request-id

Lần một: UUID server sinh. Lần hai: thu-nghiem-123 giữ nguyên — đúng logic genReqId.

02 · Preflight CORS không tới guard 
curl -s -i -X OPTIONS localhost:3000/roles -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET" | head -1

204, không phải 401 — dù /roles cần token.

03 · Ngôn ngữ do middleware quyết

Gọi một route trả bản dịch với -H "x-lang: vi" rồi -H "x-lang: en". Handler không đọc header nào — @CurrentLang() chỉ hỏi context mà I18nMiddleware đã đặt.

04 · Redact hoạt động

Đăng nhập với body có password, nhìn log — trường đó hiện **GDPR COMPLIANT**. Redact xảy ra ở middleware pino với request thô, không thể muộn hơn.
