Prototype, this, và class

Chương 1 viết X.prototype ở khắp nơi. Chương này trả lời prototype là cái gì, ở đâu ra, khác __proto__ ra sao — bằng JavaScript thuần, không NestJS — rồi mới nối ngược về decorator và metadata.

Ai nên đọc chương này
Người vấp ở chỗ "target là X.prototype" của chương 1. Chín mục đầu không có NestJS, chỉ JavaScript; mục 10 nối về decorator/metadata. Ai đã quen prototype chain thì bỏ qua, vào thẳng chương 1. Mọi đoạn code đều chạy được bằng node — nên chạy thật, prototype là thứ đọc mãi không hiểu nhưng in ra một lần là thông.
00Trả lời ngắn: vì sao class lại có prototype?
Một câu

Vì class trong JavaScript là một hàm dựng (constructor function) viết cho đẹp. Mọi hàm đều có sẵn một property tên prototype, nên class cũng có. JavaScript không có cơ chế kế thừa nào khác ngoài prototype — class chỉ là lớp áo mới trên đúng cơ chế cũ.

Nếu bạn tới đây với đúng một câu hỏi — "class là class, sao lại dính prototype?" — thì mục này trả lời gọn. Mười ba mục sau chỉ là mổ xẻ từng mảnh của câu trả lời này. Hai đoạn dưới đây tạo ra cùng một thứ: một hàm tên MyClass, và một object MyClass.prototype chứa myMethod.

cách viết ES6class 
class MyClass {
  myMethod() {}
}
cách viết ES5 — tương đươngfunction 
function MyClass() {}
MyClass.prototype.myMethod = function () {};

0.1 · prototype để làm gì

Để instance tra được method mà không cần giữ bản sao của method. Khi gọi obj.myMethod(), JavaScript tìm myMethod trên chính obj trước. Không có. Nó đi tiếp lên prototype của obj — chính là MyClass.prototype — và tìm thấy ở đó.

tra method qua chainnode 
class MyClass {
  myMethod() {
    console.log("Hello from myMethod");
  }
}

const obj = new MyClass();
obj.myMethod();  // "Hello from myMethod"

Object.getPrototypeOf(obj) === MyClass.prototype; // true
hình dung
   obj                MyClass.prototype    Object.prototype     null
┌──────────────┐   ┌──────────────────┐ ┌──────────────────┐
│ (field riêng)│──▶│ myMethod         │▶│ toString, ...    │──▶ ×
└──────────────┘   │ constructor      │ └──────────────────┘
       ▲           └──────────────────┘
  obj.myMethod() tìm ở đây trước → không có → đi theo mũi tên

Đây là lúc prototype được dùng: mỗi lần new, object mới được nối ngầm vào MyClass.prototype; và mỗi lần extends, prototype của class con được nối lên prototype của class cha, nên class con dùng lại được method của cha và ghi đè được method của cha.

0.2 · Được gì

01 · Tiết kiệm bộ nhớ
Method định nghĩa trong constructor thì mỗi instance một bản sao. Đặt trên prototype thì một triệu instance dùng chung một hàm.
02 · Kế thừa, mở rộng
Object kế thừa từ object khác bằng cách nối chain, ghi đè bằng cách đặt property cùng tên lên chính object của mình (mục 2).

0.3 · Vì sao chương này vẫn dài thêm 13 mục nữa

Câu trả lời trên đúng nhưng chưa đủ để đọc chương 1. Bốn chỗ hay vấp, mỗi chỗ có một mục riêng:

Vấp ở đâu Đọc mục
Foo.prototype với obj.__proto__ là một hay hai thứ? mục 3
new thật ra làm gì mục 4
Method lên prototype, còn field thì không — vì sao mục 5.1
class biên dịch ra đúng cái gì mục 5.3

Và câu hỏi đích của cả bộ tài liệu — vì sao decorator nhận X.prototype chứ không nhận instance — nằm ở mục 10.

01Object chỉ là một cái bảng
JavaScript thuầnví dụ 
const user = {
  name: "Thắng",
  greet() {
    return "hi";
  },
};
key value
"name" "Thắng"
"greet" [Function] — hàm cũng chỉ là một giá trị
Bỏ hết thuật ngữ đi

Object là một cái bảng tra: tên → giá trị. user.name nghĩa là "tìm dòng có key name trong bảng này". Hết. Method không phải loại đặc biệt gì — chỉ là một dòng mà value tình cờ là hàm.

02Tìm không thấy thì đi hỏi chỗ khác: prototype chain
Toàn bộ cơ chế prototype, một câu

Mỗi object có một liên kết ẩn trỏ tới một object khác. Tra key không thấy trong bảng của mình, JavaScript đi theo liên kết đó và tra tiếp ở bảng kia. Không thấy nữa thì đi tiếp. Tới cuối chuỗi vẫn không thấy → undefined.

Object bị trỏ tới đó gọi là prototype của object này. Chuỗi liên kết đó gọi là prototype chain. Dựng tay một chuỗi để thấy rõ, bằng Object.create(x) — "tạo object rỗng mà prototype là x":

chain dựng taynode 
const animal = { legs: 4, speak: () => "..." };
const dog = Object.create(animal); // dog rỗng, prototype = animal
dog.speak = () => "woof";     // dog tự có speak riêng

dog.speak();  // "woof"     ← thấy ngay trong bảng của dog
dog.legs;     // 4          ← dog không có, hỏi tiếp animal
dog.color;    // undefined  ← hết chuỗi, không thấy
dog.legs — đường đi tìm 
 ① dog                ② animal           ③ Object.prototype   ④ hết
┌────────────────┐hỏi┌───────────────┐hỏi┌─────────────────┐
│ speak: woof    │──▶│ legs: 4       │──▶│ toString, ...   │──▶ null
│ (không có legs)│   │ speak: "..."  │   │ (không có legs) │
└────────────────┘   └───────────────┘   └─────────────────┘
 object bạn viết      prototype           prototype           không ai
 tên ra để truy cập   của dog             của animal          trả lời nữa
                             ▲
             tìm thấy legs ở đây → trả 4, dừng, không hỏi tiếp
Một dây chuyền hỏi tiếp
Mỗi object biết đúng một object để hỏi khi mình không có câu trả lời. Ba điều dưới đây đều nói về một chiều duy nhất — từ object bạn viết tên ra, đi sang prototype của nó. Không có chiều ngược lại: animal hoàn toàn không biết dog tồn tại.
01 · Đọc: hỏi chính mình trước, thấy thì dừng ngay
dog.speak có sẵn trên dog nên animal.speak không bao giờ được ngó tới — nó bị che. Đó chính là "override": muốn thay một method của prototype, đặt property cùng tên lên object của mình.
02 · Ghi: luôn ghi vào chính object bạn gán
dog.legs = 3 không sửa animal.legs; nó tạo một dòng legs mới trên chính dog. Đọc thì đi tiếp sang prototype, ghi thì đứng yên tại chỗ.
03 · Chia sẻ, không copy
dog không chứa bản sao của legs — nó chỉ mượn của animal. Sửa animal.legs = 2 thì dog.legs đọc ra 2 ngay, miễn là dog chưa tự có legs riêng theo điều 02.
ba điều trên, chạy thậtnode 
dog.legs;         // 4  ← dog không có, mượn của animal
dog.legs = 3;     // ghi vào chính dog, animal không bị đụng
animal.legs;      // 4
animal.legs = 2;  // sửa animal
dog.legs;         // 3  ← dog đã có legs riêng, không hỏi animal nữa
Gặp chữ "tầng trên / tầng dưới" ở tài liệu khác thì hiểu thế nào
Nhiều người vẽ chuỗi này theo chiều dọc và gọi object bạn viết tên ra là "dưới", prototype của nó là "trên" — tức "đi lên" nghĩa là ô ② rồi ③ trong hình trên. Chương này tránh dùng hai chữ đó vì hình vẽ ngang, nhưng bạn sẽ gặp chúng ở nơi khác.

Liên kết ẩn đó chuẩn gọi là [[Prototype]]. Xem và đổi nó bằng API tử tế: Object.getPrototypeOf(dog) === animal ra true; Object.setPrototypeOf đổi được nhưng đừng dùng trong code thật — chậm.

03prototype và __proto__ là hai thứ khác nhau
Đây là chỗ gây nhầm nhiều nhất — và là lý do chính khiến chương 1 khó đọc
Hai cái tên gần giống nhau nhưng nghĩa khác hẳn. Foo.prototype không phải prototype của Foo.
Viết Nằm trên Nghĩa
obj.__proto__ mọi object prototype của chính obj — "tôi đi hỏi ai"
Foo.prototype chỉ hàm object sẽ được gán làm prototype cho instance mới của Foo
kiểm chứng
function Foo() {}
const f = new Foo();

Object.getPrototypeOf(f) === Foo.prototype;
// true  ← prototype của INSTANCE

Object.getPrototypeOf(Foo) === Function.prototype;
// true  ← prototype của chính hàm Foo
hai mũi tên khác nhau 
 f ──[[Prototype]]──▶ Foo.prototype ──▶ Object.prototype
                            ▲
                            │ .prototype  (property thường của hàm)
                          Foo
Ghim một câu

Foo.prototype là tài sản của Foo, dành cho con của Foo dùng. Mỗi lần thấy X.prototype trong chương 1 hay trong code Nest, đọc nó là "cái tủ dùng chung của mọi instance X" — không phải "class X".

04new làm đúng bốn việc

new Foo(a, b) không phải phép màu. Nó là bốn bước, viết tay được:

new, viết bằng tay
function myNew(Ctor, ...args) {
  // 1. object rỗng, prototype = Ctor.prototype
  const obj = Object.create(Ctor.prototype);
  // 2. chạy Ctor với this = obj
  const ret = Ctor.apply(obj, args);
  // 3-4. trả obj, trừ khi Ctor return object
  return typeof ret === "object" && ret !== null
    ? ret
    : obj;
}
và nó chạy đúng
function User(name) {
  this.name = name;  // ghi vào INSTANCE
}
User.prototype.greet = function () {
  return `hi ${this.name}`;  // ghi vào TỦ CHUNG
};

const u = myNew(User, "Thắng");
u.greet();          // "hi Thắng"
Object.keys(u);    // ["name"] ← greet KHÔNG trên u
Vì sao method lại đặt ở prototype
name nằm trên instance. greet nằm trên User.prototype — một bản duy nhất cho cả triệu instance. Một hàm, dùng chung, thay vì copy vào từng object.
05class chỉ là cú pháp đẹp cho đúng cơ chế đó
class
class User {
  constructor(name) {
    this.name = name;
  }
  greet() {
    return `hi ${this.name}`;
  }
}
vẫn là constructor + prototype 
typeof User
→ "function"                          ← class LÀ hàm

User.prototype.greet
→ [Function: greet]                   ← method nằm ở đây

new User("a").greet === User.prototype.greet

class không mang lại một mô hình object mới — vẫn là constructor + prototype, chỉ khác cách viết (và thêm vài luật chặt hơn: phải gọi bằng new, chạy ở strict mode, method không enumerable).

5.1 · Method nằm trên prototype, field nằm trên instance

in ra để thấy
class Dto {
  name = "chưa có";  // field → trên INSTANCE
  age;                // field → cũng vậy
  validate() {}       // method → trên Dto.prototype
}

Object.getOwnPropertyNames(Dto.prototype);
// ["constructor", "validate"]
Object.getOwnPropertyNames(new Dto());
// ["name", "age"]
Viết trong class Sống ở đâu Có từ lúc nào
greet() {} X.prototype lúc class được định nghĩa (import file)
name = "x" từng instance lúc new X() chạy
static ten = 1 chính X lúc class được định nghĩa
get full() {} X.prototype lúc class được định nghĩa
Câu quan trọng nhất của cả chương
Lúc class vừa được định nghĩa, method đã tồn tại nhưng field thì chưa — chưa có instance nào cả. Giữ câu này, mục 10.3 sẽ tự sáng.

5.2 · Vì sao Object.keys(prototype) ra rỗng

output
class A { hello() {} }

Object.keys(A.prototype)
→ []                                  ← ??

Object.getOwnPropertyNames(A.prototype)
→ ["constructor", "hello"]
Không phải hello biến mất
Method của class được đặt với cờ enumerable: false, và Object.keys / for...in / spread chỉ nhìn property enumerable. Muốn liệt kê method thì dùng Object.getOwnPropertyNames.

Chương 1 có một đoạn cùng họ nguyên nhân này: Object.keys(...getManageProducts) ra []. Object.keys không phải cách để soi cấu trúc thật của object.

5.3 · Bản chất của "syntax sugar": nhìn code sau khi biên dịch

"Sugar" nghĩa là: cú pháp mới, không có cơ chế mới. Cách kiểm chứng duy nhất là nhìn thứ TypeScript nhả ra. Dự án đặt target: ES2021 (tsconfig.json:11), Node hiểu class, nên tsc giữ nguyên từ khoá — nhưng vẫn phải kéo field và decorator ra ngoài, vì hai thứ đó không phải cú pháp ES2021.

nguồnTypeScript 
class Foo extends Base {
  count = 0;
  static total = 1;
  constructor(private readonly dep: string) {
    super();
  }
  @SetMetadata("k", "v")
  hello(id: string): string {
    return id;
  }
}
tsc --target ES2021 nhả rarút gọn 
class Foo extends Base {
  constructor(dep) {
    super();
    this.dep = dep;    // parameter property → gán
    this.count = 0;    // field → gán, lúc new
  }
  hello(id) { return id; }
}
Foo.total = 1;          // static → gán lên class

__decorate([
  SetMetadata("k", "v"),
  __metadata("design:type", Function),
  __metadata("design:paramtypes", [String]),
  __metadata("design:returntype", String),
], Foo.prototype, "hello", null);
//  ↑ target       ↑ key      ↑ desc: tự lấy
01 · Field thành dòng gán trong constructor
Bằng chứng cho mục 5.1: count chỉ tồn tại khi new chạy. Kiểu (: string) biến mất hoàn toàn — TypeScript xoá kiểu, không dịch kiểu.
02 · Decorator thành một lời gọi hàm sau class
Với Foo.prototype và "hello" là tham số literal. Khi bạn thấy target === Foo.prototype ở chương 1, giờ bạn biết nó đến từ đâu: người viết tsc gõ đúng chữ đó vào.
03 · __metadata("design:type", …)
Là thứ cờ emitDecoratorMetadata thêm vào — TypeScript tự dán kiểu lên cùng chỗ với decorator của bạn. Chi tiết ở phụ lục A §5.
04 · __decorate ưu tiên Reflect.decorate
Mà reflect-metadata cung cấp đúng hàm đó. Nên trong dự án, decorator của bạn thực tế được thư viện áp, không phải đoạn for dự phòng.
tsc --target ES5 — nơi không có class 
var Foo = (function (_super) {
  __extends(Foo, _super);          // nối hai chain (mục 8)
  function Foo(dep) {
    var _this = _super.call(this) || this;
    _this.dep = dep;
    _this.count = 0;
    return _this;
  }
  Foo.prototype.hello = function (id) {
    return id;
  };                                 // method = gán lên prototype (mục 4)
  Foo.total = 1;
  __decorate([...], Foo.prototype, "hello", null);
  return Foo;
})(Base);
Thấy hết đáy
Đúng đoạn function User + User.prototype.greet = … ở mục 4. Không có gì khác.

Với target ≥ ES2022 và useDefineForClassFields: true, field được giữ nguyên cú pháp và định nghĩa bằng Object.defineProperty thay vì gán — khác một chi tiết về accessor, không đổi kết luận "field nằm trên instance".

Vậy class thêm gì ngoài cách viết? Vài luật chặt hơn, tất cả kiểm chứng được bằng node:

Luật Bằng chứng Vì sao đáng nhớ
Phải gọi bằng new A() → TypeError: Class constructor A cannot be invoked without 'new' function-style thì User("x") chạy êm và ghi name lên globalThis
Không hoisting new B() trước class B {} → ReferenceError: Cannot access 'B' before initialization function declaration thì gọi trước khai báo được
Body luôn strict mode gán biến chưa khai báo trong method → ReferenceError và this không bị boxing (mục 9.3)

06this được quyết định lúc gọi, không phải lúc viết

Method nằm trên prototype và dùng chung, vậy this.name lấy name của ai? Của object đứng trước dấu chấm lúc gọi.

cùng một hàm, this khác nhau 
const u1 = new User("A");
const u2 = new User("B");

u1.greet();  // "hi A"  ← this = u1
u2.greet();  // "hi B"  ← this = u2
tách ra khỏi object là mất this 
const g = u1.greet;
g();            // TypeError: ... of undefined
g.call(u1);     // "hi A" ← chỉ định this thủ công
u1.greet.bind(u1)();  // "hi A" ← đóng cứng
Gặp ở đâu trong dự án
Truyền this.handler làm callback (cho setTimeout, event listener, array.map) thì phải .bind(this) hoặc bọc arrow function — không thì this rỗng.
Arrow function: được this, mất prototype
Arrow không có this riêng, nó lấy this của nơi được viết. Nên handler = () => {...} luôn đúng this — đổi lại hàm đó nằm trên instance, không trên prototype, và mục 10.1 sẽ cho thấy method decorator của Nest không dán được lên loại đó.
07Property descriptor — bản mô tả của một property

Mỗi dòng trong bảng object không chỉ có value. Nó có một bản mô tả gồm value và ba cờ:

output
class A { hello() {} }
Object.getOwnPropertyDescriptor(A.prototype, "hello")

{ value: [Function: hello],
  writable: true,
  enumerable: false,
  configurable: true }
Trường Nghĩa
value chính giá trị — ở đây là bản thân hàm
writable gán lại được không
enumerable có hiện trong Object.keys / for...in không
configurable xoá / đổi mô tả được không
01 · Không phải bản sao
descriptor.value === A.prototype.hello ra true. value là đúng hàm đó, không phải bản copy.
02 · Không có thì không có mô tả
Property chưa tồn tại thì getOwnPropertyDescriptor trả undefined. Nghe hiển nhiên, nhưng đây chính là lời giải cho "vì sao property decorator không có tham số thứ ba" (mục 10.3).
08extends chỉ là nối thêm một mắt vào chain
hai chain song song

  ping() { return "pong"; }
}
class Child extends Base {

Object.getPrototypeOf(Child.prototype) === Base.prototype;
// true ← chain của INSTANCE

new Child() ─▶ Child.prototype ─▶ Base.prototype ─▶ Object.prototype ─▶ null

Trong dự án
Chưa có controller nào extends controller khác, nhưng DTO thì có — RolePaginationQueryDto extends PaginationQueryDto (src/dtos/role/role.dto.ts:17). Nhờ chain đó mà DTO con thừa hưởng luôn rule validation của page / limit khai ở cha.

Hễ có chuỗi là có "đi ngược lên tìm" — và Reflect.getMetadata đi ngược đúng chuỗi này (mục 10.5).

09Boxing: primitive không phải object, nhưng vẫn .length được

Có bảy kiểu primitive — string, number, boolean, bigint, symbol, undefined, null. Chúng không phải object: không có bảng key → value, không có liên kết [[Prototype]]. Vậy tại sao "abc".length chạy?

Boxing — đóng hộp

Khi bạn dùng . lên một primitive, JavaScript tạm tạo một object bao (new String("abc")) quanh nó, tra property trên object đó — theo prototype chain bình thường — rồi vứt object bao đi.

"abc".toUpperCase() thực ra là 
1. tạo hộp:  box = new String("abc")     (tạm, vô hình)
2. tra:      box.toUpperCase
             → không có trên box
             → lên String.prototype → thấy
3. gọi:      String.prototype.toUpperCase, this = box
4. vứt hộp:  box biến mất; giữ lại "ABC"
method của string nằm trên String.prototype 
Object.getPrototypeOf("abc") === String.prototype; // true

String.prototype.shout = function () {
  return this.toUpperCase() + "!";
};
"hi".shout(); // "HI!" — thêm vào tủ là mọi string đều có

Đúng cái tủ dùng chung ở mục 3, chỉ khác là chủ tủ là hàm dựng sẵn String.

9.1 · Ba hệ quả nhìn thấy được

01 · Gán property lên primitive là mất
Hộp bị vứt sau mỗi phép ., nên thứ bạn gán nằm trên một hộp đã chết. 
const s = "abc";
s.foo = 1;  // sloppy: im lặng; strict: TypeError
s.foo;      // undefined — hai hộp khác nhau
02 · Hộp thật ≠ primitive
new String("a") là object thật, sống lâu. 
typeof "a";              // "string"
typeof new String("a");  // "object"
new String("a") == "a";   // true  — == mở hộp
new String("a") === "a";  // false
Boolean(new Boolean(false)); // true!

Đừng bao giờ viết new String(…) trong code thật. Chúng chỉ tồn tại để engine có chỗ treo String.prototype.

03 · null và undefined không có hộp
Không có constructor bao, nên . lên chúng ném lỗi. 
null.length;
// TypeError: Cannot read properties
//            of null (reading 'length')

Nguồn của phần lớn TypeError trong log: biến đáng ra là string/object nhưng đang là null, và không có hộp nào để cứu.

9.2 · 5.toFixed() là lỗi cú pháp, (5).toFixed() thì không

bẫy parser
(5).toFixed(2); // "5.00"
5..toFixed(1);  // "5.0" — chấm đầu thuộc số
Boxing áp dụng cho số y như chuỗi, nhưng 5. được đọc là số thập phân 5.0, nên 5.toFixed là lỗi cú pháp. Bọc ngoặc hoặc dùng hai dấu chấm.

9.3 · Boxing và this: sloppy khác strict

this khi thứ đứng trước là primitive 
function sloppy() { return typeof this; }
function strict() { "use strict"; return typeof this; }

sloppy.call("x"); // "object" — this bị boxing
strict.call("x"); // "string" — giữ nguyên primitive
Trong dự án bạn không gặp this bị boxing
Body của class luôn strict (mục 5.3), ES module luôn strict, và tsc với module: commonjs chèn "use strict" vào đầu mỗi file. Nhưng đọc code thư viện cũ kiểu String.prototype.foo = function () { this… } không strict thì this ở đó là hộp, không phải chuỗi.

9.4 · string với String — và vì sao TypeScript phân biệt

Viết Là gì Dùng khi
string kiểu primitive luôn luôn, trong annotation
String kiểu của object hộp, đồng thời là hàm dựng không bao giờ trong annotation
Một chỗ String viết hoa xuất hiện hợp lệ — và dẫn thẳng về metadata
Annotation name: String không sai cú pháp nhưng sai nghĩa; lint của dự án chặn (@typescript-eslint/no-wrapper-object-types). Nhưng khi TypeScript dán kiểu của field name: string vào bảng ẩn, nó không thể dán chữ string — kiểu bị xoá khi biên dịch, còn bảng ẩn cần một giá trị runtime. Giá trị runtime duy nhất đại diện được cho "chuỗi" là hàm dựng String. Chi tiết ở mục 10.8.
10Nối về decorator và metadata
Ba câu mang sang chương 1
  1. X.prototype là cái tủ dùng chung của mọi instance X (mục 3).
  2. Method sống trên prototype ngay khi class được định nghĩa; field chỉ sống trên instance và chỉ khi new chạy (mục 5.1).
  3. Có chuỗi prototype thì có chuyện đi ngược lên tìm (mục 2, mục 8).

10.1 · Vì sao method decorator nhận prototype

TypeScript
function MethodDec(target, key, desc) {
  target === Foo.prototype;             // true
  desc.value === Foo.prototype.hello;   // true
}

class Foo {
  @MethodDec hello() {}
}
Không phải quy ước lạ
Decorator chạy lúc class được định nghĩa — chưa có instance nào. Muốn chỉ cho decorator "method hello nằm chỗ này" thì chỉ có một địa chỉ tồn tại vào thời điểm đó: Foo.prototype — đúng chỗ method thật sự nằm (mục 5.1).

Cũng vì vậy, method viết dạng handler = () => {} nằm trên instance nên chưa tồn tại khi decorator chạy — không dán decorator kiểu method lên nó được.

10.2 · Vì sao metadata dùng chung cho mọi instance

@RequirePermission thực chất là 
Reflect.defineMetadata(
  "required_permission",
  "product:read:own",
  ManageProductController.prototype.getManageProducts,
  // ↑ MỘT hàm duy nhất cho cả nghìn request
);
Hệ quả: cấm lưu dữ liệu theo-request
Chỉ có một ManageProductController.prototype.getManageProducts cho cả nghìn request, nên nhãn dán lên hàm đó là nhãn cho tất cả. Hai request đồng thời ghi metadata sẽ đè lẫn nhau. Dữ liệu theo-request thuộc về object request (chương 3 §9).

10.3 · Vì sao property decorator không có descriptor

Nhìn lại bảng chương 1 §2.2: property decorator chỉ nhận (target, key), tham số thứ ba là undefined. Ghép mục 5.1 với mục 7 là ra:

Class vừa định nghĩa
field chưa tồn tại — nó chỉ sinh ra khi new chạy
→
Không có property
thì không có descriptor để trao
→
Nên chỉ làm được một việc
ghi nhãn vào toạ độ (prototype, tên field)
src/dtos/role/role.dto.ts:95-101dự án 
export class CreateRoleRequestDto {

  name: string;

Hai decorator, hai nhãn, một toạ độ
Cả hai cùng ghi vào (CreateRoleRequestDto.prototype, "name"). Không cái nào đọc được giá trị của name — lúc chúng chạy chưa có instance nào. Chúng chỉ để lại chỉ dẫn; ValidationPipe mới là người đọc, mỗi request (chương 7).

10.4 · descriptor.value và context.getHandler() là cùng một hàm

mắt nối cả hệ thống 
lúc định nghĩa class        lúc có request

10.5 · Vì sao metadata kế thừa được

getMetadata đi lên, getOwnMetadata không 
@SetMetadata("tag", "từ cha")
class BaseController {}
class ChildController extends BaseController {}

Reflect.getMetadata("tag", ChildController);
// "từ cha"   ← đi lên theo chain
Reflect.getOwnMetadata("tag", ChildController);
// undefined  ← chỉ nhìn chính nó
Không phải tính năng riêng của reflect-metadata
"Decorator trên class cha được class con thừa hưởng" (chương 1 §11) là prototype chain, lần thứ ba trong chương này. Đọc metadata cũng chỉ là một phép tra key — không thấy thì đi lên.

10.6 · Script quét route của dự án đi đúng trên prototype

Chỗ nhìn thấy prototype rõ nhất trong code thật là hàm kiểm tra lúc khởi động — nó phải tìm mọi handler của mọi controller để chắc chắn không route nào thiếu @RequirePermission.

src/shared/utils/collect-route-permissions.util.ts:48-67dự án 
const prototype = controllerClass.prototype as Record<string, unknown>;

for (const methodName of metadataScanner.getAllMethodNames(prototype)) {
  const handler = prototype[methodName];

  if (typeof handler !== "function") continue;
  if (Reflect.getMetadata(PATH_METADATA, handler) === undefined) continue;

  const key = reflector.getAllAndOverride<PermissionKey | undefined>(
    PERMISSION_KEY,
    [handler, controllerClass],
  );
}
Dòng Là gì theo chương này

prototype[methodName] lấy chính hàm handler, cùng object guard sẽ nhận lúc chạy (mục 10.4)
Reflect.getMetadata(PATH_METADATA, ...) nhãn @Get() đã dán lên hàm đó lúc import file
[handler, controllerClass] tra method trước, không có thì tra class — đúng thứ tự "dưới lên" (mục 2)

10.7 · Vì sao DI đọc được kiểu tham số constructor

Dòng lệch trong bảng chương 1
Decorator trên tham số constructor nhận target là constructor, key là undefined. Mục 3 giải thích: constructor là chính hàm class, nó không phải một entry trên prototype nên không có tên property để đưa vào key.
nên metadata dán lên chính class

// [ [Function: ManageProductService] ]
Đó là cách Nest biết constructor(private readonly svc: ManageProductService) cần nhận cái gì — đọc mảng kiểu này rồi tìm provider tương ứng (chương 6).

10.8 · design:type là hàm dựng, không phải tên kiểu — hệ quả của boxing

Chương 1 §6.7 in ra design:type của 'name' = [class String]. Ghép mục 9.4 với mục 5.3 là hiểu vì sao lại là String viết hoa:

Kiểu string bị xoá
lúc biên dịch (mục 5.3) — không còn gì để dán
→
Bảng ẩn chỉ nhận giá trị JS
thứ duy nhất vừa tồn tại ở runtime vừa "có nghĩa là chuỗi" là hàm dựng String
→
__metadata("design:type", String)
và class-validator so === String

Cùng logic cho toàn bảng — mỗi kiểu TypeScript được ánh xạ về hàm dựng gần nhất, và thứ gì không có hàm dựng thì gộp về Object:

Annotation design:type Vì sao
string / "a" | "b" String hàm dựng của hộp
number / enum số Number như trên
boolean Boolean như trên
string[] Array mất tham số phần tử — validator không biết là string[]

string | number Object như trên

any Object không biết gì
Promise<number> (return) Promise mất tham số bên trong
Hai quy tắc dự án sinh ra từ hai dòng cuối bảng
Không inject qua interface (DI chỉ nhận được Object, không biết tìm provider nào — chương 6) và @IsArray() phải kèm { each: true } (validator chỉ thấy Array — chương 7). Toàn bộ cơ chế ghi/đọc của bảng ẩn nằm ở phụ lục A.

12Sáu nhầm lẫn phổ biến
Nhầm Thực tế
"Foo.prototype là prototype của Foo" Không. Nó là prototype của instance Foo. Prototype của Foo là Function.prototype.
"class là mô hình OOP mới, khác prototype" Không. class là cú pháp gọn cho constructor + prototype. typeof class vẫn là "function".
"Kế thừa là copy method từ cha xuống con" Không copy gì. Chỉ nối thêm một mắt vào chain; sửa method ở cha là con thấy ngay.
"Method dán decorator được thì field cũng vậy" Khác nhau. Method có trên prototype lúc class định nghĩa; field thì chưa tồn tại → không có descriptor.
"String có method nên string là object" Không. String là primitive; method nằm trên String.prototype, được tra qua một hộp tạm rồi vứt (mục 9).
"design:type lưu tên kiểu TypeScript" Không. Kiểu bị xoá lúc biên dịch; nó lưu hàm dựng gần nhất (String, Array, Object) (mục 10.8).
