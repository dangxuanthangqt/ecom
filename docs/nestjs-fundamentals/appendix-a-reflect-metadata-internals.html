Phụ lục A

reflect-metadata bên trong

Chương 1 gọi nó là "bảng ẩn của thủ thư" và dừng ở cách dùng. Phụ lục này mở nắp: bảng ẩn là cấu trúc dữ liệu gì, getMetadata đi ngược chain thế nào, TypeScript tự dán những gì — và những chỗ hành vi thư viện quyết định hành vi của Nest.

Đọc sau chương 0 và chương 1
Mọi trích dẫn mã nguồn lấy từ reflect-metadata@0.2.2 đang cài trong dự án (node_modules/reflect-metadata/Reflect.js), kèm số dòng để bạn mở ra đối chiếu.
01Nó là gì, và vì sao phải import một lần
polyfill vá lên global Reflect 
import "reflect-metadata"; // không import tên gì — chỉ chạy file

typeof Reflect.defineMetadata; // "function" (trước import: "undefined")
typeof Reflect.getMetadata;    // "function"
typeof Reflect.decorate;       // "function" ← mục 6
typeof Reflect.metadata;       // "function" ← decorator factory có sẵn
Polyfill cho một đề xuất chuẩn
Metadata Reflection API, của Ron Buckton — người cũng viết phần decorator của TypeScript. Đề xuất chưa vào ECMAScript, nên thư viện tự cài API đó lên object toàn cục Reflect.
Ba điều đi kèm
  • Một lần cho cả tiến trình. @nestjs/core import ở đầu, nên src/ không có dòng này; script ts-node tự viết thì phải tự import.
  • Ba bản build: Reflect.js (đầy đủ), ReflectLite.js (bỏ polyfill Map/Set), ReflectNoConflict.js (không vá global). Nest dùng bản đầy đủ.
  • Không chạm vào object của bạn. Không thêm property, không đổi prototype. Dữ liệu nằm ở nơi khác — mục 2.
02Bảng ẩn là ba tầng Map lồng trong một WeakMap
Một tầng gián tiếp nữa, nói trước cho khỏi bất ngờ
WeakMap ở dòng 1013 không phải biến toàn cục đứng một mình: nó nằm bên trong hàm CreateMetadataProvider(registry) (Reflect.js:1010). Mọi defineMetadata / getMetadata đều đi qua một registry để hỏi "ô này thuộc provider nào" rồi mới chạm tới WeakMap đó. Khi trong tiến trình chỉ có một bản reflect-metadata — trường hợp của dự án này — thì chỉ có đúng một provider, nên hình ba tầng dưới đây mô tả đúng cái bạn quan sát được. Vì sao cần lớp registry: xem mục 7.
Reflect.js:1013, 1029-1051rút gọn 
var metadata = new _WeakMap(); // [[Metadata]] internal slot

function GetOrCreateMetadataMap(O, P, Create) {
  var targetMetadata = metadata.get(O);   // tầng 1: TARGET
  if (IsUndefined(targetMetadata)) {
    if (!Create) return undefined;
    targetMetadata = new _Map();
    metadata.set(O, targetMetadata);
  }
  var metadataMap = targetMetadata.get(P); // tầng 2: PROPERTY KEY
  if (IsUndefined(metadataMap)) {          //   undefined = cả quyển
    if (!Create) return undefined;
    metadataMap = new _Map();
    targetMetadata.set(P, metadataMap);
  }
  return metadataMap;                        // tầng 3: key → value
}

Ba điều rút ra
  1. "Cả quyển" (chương 1 §6.5) là hàng có key undefined ở tầng 2. Map chấp nhận undefined làm key.
  2. Class, hàm, prototype là ba entry riêng ở tầng 1 — ba object khác nhau. Đó là chương 1 §6.4.
  3. defineMetadata hai lần cùng key là Map.set hai lần → ghi đè im lặng.

03Vì sao là WeakMap

WeakMap khác Map ở một điểm: key phải là object, và không giữ object đó sống. Khi không còn ai tham chiếu tới target, garbage collector dọn target và dọn luôn hàng metadata của nó.

Nếu dùng… Thì…
Map thường mọi class từng được dán metadata sống mãi trong bộ nhớ, kể cả class tạo động rồi bỏ
property ẩn trên object (__meta) lộ ra khi Object.getOwnPropertyNames, đụng tên, không dán được lên object frozen
WeakMap vô hình với target, tự dọn, dán được lên bất kỳ object nào kể cả frozen
Đổi lại: không liệt kê được
WeakMap không iterate được. Đó là lý do Nest phải tự quét: DiscoveryService + MetadataScanner đi qua từng controller, từng method trên prototype rồi mới gọi getMetadata từng cái (chương 2). Không có hàm "cho tôi mọi handler có required_permission" — kho chứa không hỗ trợ câu hỏi đó.
key phải là object
Reflect.defineMetadata("k", 1, "str");    // TypeError
Reflect.defineMetadata("k", 1, () => {}); // OK — hàm là object
04getMetadata đi ngược chain — đọc thẳng mã nguồn
Reflect.js:591-599gộp dòng if, logic nguyên vẹn 
function OrdinaryGetMetadata(MetadataKey, O, P) {
  var hasOwn = OrdinaryHasOwnMetadata(MetadataKey, O, P);
  if (hasOwn) return OrdinaryGetOwnMetadata(MetadataKey, O, P);
  var parent = OrdinaryGetPrototypeOf(O); // Object.getPrototypeOf
  if (!IsNull(parent))
    return OrdinaryGetMetadata(MetadataKey, parent, P); // đệ quy
  return undefined;
}
Đúng thuật toán tra property của JavaScript
Chương 0 §2, chỉ khác chỗ tra: thay vì tra bảng property của O, nó tra metadata.get(O).get(P). Cùng chain, cùng thứ tự dưới-lên, cùng dừng ở null.

getOwnMetadata là phiên bản không có hai dòng parent. getMetadataKeys gộp key của O và mọi tầng trên, loại trùng.

4.1 · Hệ quả với SetMetadata: dán lên hàm thì override là mất

Chain đi theo Object.getPrototypeOf(O). Vậy O là gì quyết định có kế thừa hay không:

Dán lên… Chain của O Class con…
class (@Controller, @SetMetadata trên class) Child → Base → Function.prototype đọc được nhãn của cha — chương 0 §8, chain thứ hai
hàm method (SetMetadata dán lên descriptor.value) hàm → Function.prototype không override → cùng hàm → đọc được; override → hàm mới, không có gì
(prototype, tên) (Reflect.metadata, design:type) Child.prototype → Base.prototype đọc được dù con có override, vì tra theo tên
kiểm chứng
class Base {
  @SetMetadata("perm", "a") hello() {}
  @SetMetadata("perm", "b") keep() {}
}
class Child extends Base {
  hello() {} // override
}

Child.prototype.keep === Base.prototype.keep;        // true
Reflect.getMetadata("perm", Child.prototype.keep);  // "b"
Reflect.getMetadata("perm", Child.prototype.hello); // undefined — hàm mới

Reflect.defineMetadata("tag", "x", Base.prototype, "hello");
Reflect.getMetadata("tag", Child.prototype, "hello");   // "x" — dù override
Ý nghĩa thực tế cho dự án
Nếu ngày nào có BaseController với @RequirePermission trên method, và controller con override method đó, nhãn không đi theo. Guard không thấy required_permission → PermissionCoverageService chặn app khởi động (fail-closed, chương 3). Cách đúng: dán lại trên method con — hoặc dán trên class nếu cả controller cùng một quyền, vì getAllAndOverride([handler, class]) sẽ rơi xuống class.

4.2 · Đọc từ instance vẫn được

vì getPrototypeOf(instance) === Class.prototype 
Reflect.defineMetadata("tag", "x", Base.prototype, "hello");
Reflect.getMetadata("tag", new Base(), "hello");    // "x"
Reflect.getOwnMetadata("tag", new Base(), "hello"); // undefined
Nest không dùng cách này (Reflector nhận hàm handler và class), nhưng nó cho thấy bảng ẩn không có khái niệm riêng về kế thừa — nó mượn hoàn toàn của prototype chain.
05Ba nhãn TypeScript tự dán: design:type, design:paramtypes, design:returntype
emitDecoratorMetadata chèn vào mảng decorator 
__decorate([
  SetMetadata("k", "v"),                       // của bạn
  __metadata("design:type", Function),        // tsc thêm
  __metadata("design:paramtypes", [String]),  // tsc thêm
  __metadata("design:returntype", String),    // tsc thêm
], Foo.prototype, "hello", null);
__metadata = Reflect.metadata — Reflect.js:189 
function metadata(metadataKey, metadataValue) {
  function decorator(target, propertyKey) {
    OrdinaryDefineOwnMetadata(metadataKey, metadataValue, target, propertyKey);
  }
  return decorator;
}
// nhận (target, propertyKey) → dán theo (prototype, tên), KHÔNG dán lên hàm
// → design:* nằm hàng khác required_permission; kế thừa được dù override
Nhãn Dán ở Giá trị Ai đọc
design:type property, method hàm dựng của kiểu class-validator, class-transformer, swagger
design:paramtypes method, class (constructor) mảng hàm dựng từng tham số DI container (class), pipes (method)
design:returntype method hàm dựng kiểu trả về hầu như không ai

5.1 · Chỉ dán khi có decorator ở đúng chỗ đó

không decorator → không __decorate → không design:* 
@C() class Dto    { constructor(dep: Dep) {} }
class NoDeco      { constructor(dep: Dep) {} }

Reflect.getMetadata("design:paramtypes", Dto);    // [Dep]
Reflect.getMetadata("design:paramtypes", NoDeco); // undefined
Đây là toàn bộ lý do @Injectable() tồn tại
Bản thân nó chỉ dán một cờ gần như vô dụng; việc thật của nó là ép tsc sinh design:paramtypes cho constructor. Bỏ nó khỏi một service có dependency → Nest báo Nest can't resolve dependencies of the RoleService (?). Cùng lý do cho từng field DTO: class-validator cần design:type nên mỗi field phải có ít nhất một decorator.

5.2 · Kiểu nào ra hàm dựng nào

Kiểu TypeScript bị xoá khi biên dịch; thứ còn lại để dán phải là giá trị runtime, và giá trị gần nhất là hàm dựng (chương 0 §10.8). Đo trực tiếp với tsc 5.7.3, strict: true:

Annotation Nhả ra Ghi chú
string, "a" | "b" String literal union cùng kiểu gốc → kiểu gốc
number, enum số Number
boolean Boolean
enum chuỗi String
string[] Array mất phần tử — validator phải được bảo { each: true }
Date, class bất kỳ chính class đây là thứ DI cần
name?: string String ? không đổi kiểu
string | null Object với strictNullChecks, null là kiểu riêng → union
string | number Object không có hàm dựng chung
interface, type alias object Object không tồn tại ở runtime
any, unknown Object
Promise<T> (return) Promise mất T
void (return) undefined
DI không inject được qua interface
constructor(private repo: IRoleRepository) → design:paramtypes là [Object] → Nest không biết tìm provider nào. Phải dùng token + @Inject(TOKEN) — chương 6.
string | null làm validator mù
design:type là Object; @IsString() vẫn chạy vì không dựa vào nó, nhưng class-transformer không còn gì để dựa khi ép kiểu. Nên viết field?: string + @IsOptional().
Promise<PageDto<T>> chỉ còn Promise
Swagger không tự suy ra response type — đó là lý do @ApiPageOkResponse({ type: … }) phải khai type tường minh.

5.3 · Import vòng → undefined

__metadata("design:paramtypes", [RoleService]) được đánh giá lúc file load. Nếu a.ts import b.ts và b.ts import lại a.ts, thì tại thời điểm class trong b.ts được định nghĩa, binding RoleService có thể chưa được gán (module a đang load dở) → mảng thành [undefined].
dấu hiệu: chữ ? đúng vị trí 
Nest can't resolve dependencies of the X (?).
Please make sure that the argument at index [0]
is available
Cách sửa
Phá vòng import (thường đúng hơn), hoặc @Inject(forwardRef(() => RoleService)) để hoãn việc đọc binding tới lúc gọi.
06Reflect.decorate — thư viện cũng là người áp decorator
helper __decorate mà tsc chèn vào đầu file 
if (typeof Reflect === "object" && typeof Reflect.decorate === "function")
  r = Reflect.decorate(decorators, target, key, desc);   // ← nhánh này chạy
else
  for (var i = decorators.length - 1; i >= 0; i--) ...  // dự phòng

return c > 3 && r && Object.defineProperty(target, key, r), r;
// ↑ ghi descriptor về prototype sau khi áp
Trong mọi app Nest, thư viện áp decorator của bạn
Hai bản làm cùng việc: duyệt mảng từ cuối lên đầu ("áp từ dưới lên" ở chương 1 §4), với method thì truyền descriptor và cho phép decorator trả descriptor mới; cuối cùng Object.defineProperty ghi về prototype.
Decorator có thể thay hẳn hàm
SetMetadata trả descriptor nguyên, nhưng @Retry(), @Cache() của nhiều thư viện gán descriptor.value = wrapper. Khi đó context.getHandler() trả về wrapper, và metadata dán lên hàm gốc trước wrapper sẽ mất. Thứ tự decorator lúc này có ý nghĩa.
07Registry: nhiều bản copy thư viện vẫn dùng chung một bảng
WeakMap metadata ở mục 2 là biến cục bộ trong closure của Reflect.js. Hai bản reflect-metadata trong node_modules → hai WeakMap riêng → decorator dán vào bản A, Nest đọc bản B → undefined toàn tập. Phiên bản 0.2.x giải quyết bằng một registry treo trên chính Reflect.
Reflect.js:83, 994-1001 
var registrySymbol = Symbol.for("@reflect-metadata:registry");
// ...
metadataRegistry = root.Reflect[registrySymbol]; // đã có? dùng chung
// chưa có → tạo và Object.defineProperty(root.Reflect, registrySymbol, …)

// bạn nhìn thấy nó:
Object.getOwnPropertySymbols(Reflect).map(String);
// [ "Symbol(Symbol.toStringTag)", "Symbol(@reflect-metadata:registry)" ]
Dự án hiện chỉ có một bản
node_modules/.pnpm/reflect-metadata@0.2.2 — registry chỉ có một provider. Nhưng khi thêm thư viện kéo theo reflect-metadata@0.1.x (không có registry), hai bên sẽ không thấy nhau — triệu chứng là decorator chạy mà getMetadata trả undefined. pnpm why reflect-metadata là lệnh đầu tiên nên gõ.
08Bảng tra API đầy đủ

Tất cả đều có hai dạng: (key, [value,] target) cho "cả quyển" và (key, [value,] target, propertyKey) cho "một trang".

Hàm Đi ngược chain? Trả về Ghi chú
defineMetadata(key, value, target[, p]) — void Map.set — ghi đè im lặng
getMetadata(key, target[, p]) có value / undefined thuật toán mục 4
getOwnMetadata(key, target[, p]) không value / undefined
hasMetadata(key, target[, p]) có boolean phân biệt "không có" với "có, giá trị undefined"
hasOwnMetadata(key, target[, p]) không boolean
getMetadataKeys(target[, p]) có any[] gộp own + cha, loại trùng, own đứng trước
getOwnMetadataKeys(target[, p]) không any[]
deleteMetadata(key, target[, p]) không boolean chỉ xoá own
metadata(key, value) — decorator dán theo (target, p); là thứ __metadata gọi
decorate(decorators, target[, p, desc]) — class / descriptor áp mảng từ cuối lên; là thứ __decorate gọi

Nest bọc bốn hàm đầu trong Reflector và thêm getAll, getAllAndMerge, getAllAndOverride — chỉ là vòng lặp getMetadata qua một mảng target rồi gộp kết quả (chương 2).

09Những điều hành vi thư viện quyết định cho Nest
Thư viện làm… Nên Nest…
Kho là WeakMap, không liệt kê được phải có DiscoveryService + MetadataScanner quét prototype từng controller (chương 2)
Tầng 1 keyed theo object metadata của class, hàm, prototype là ba nơi riêng; getAllAndOverride([handler, class]) phải hỏi hai nơi
getMetadata đi theo Object.getPrototypeOf decorator trên class cha kế thừa được; trên method thì chỉ khi không override (mục 4.1)
